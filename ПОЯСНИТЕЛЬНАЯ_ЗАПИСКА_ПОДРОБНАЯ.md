# Подробная пояснительная записка к проекту ProjectTracker

## Титульный блок

- **Проект:** `ProjectTracker`
- **Предметная область:** контроль выполнения учебных проектов
- **Тип:** веб-приложение с серверной рендеринг-архитектурой
- **Курс:** API и WEB
- **Автор:** Матвей Конин
- **Дата версии записки:** 03.05.2026

---

## Аннотация

Проект `ProjectTracker` разработан для организации и контроля учебных проектов в связке «учитель-ученик».  
Система объединяет постановку этапов, фиксацию прогресса, обмен сообщениями и формирование отчетности в одном веб-интерфейсе.  
В реализации используются две базы данных `SQLite`: основная (предметные сущности) и сервисная (сообщения и журналы).  
Для работы с данными применяется ORM (`Flask-SQLAlchemy`), для веб-части — `Flask + Jinja2 + Bootstrap 5`.  
Роли пользователей разделены на уровне маршрутов и проверок доступа к проектам, этапам, сообщениям и API-методам.  
В текущей версии импорт этапов и экспорт отчетов реализованы в формате `XLSX` с валидацией и бизнес-ограничениями.  
Результат — рабочая система для учебного процесса с практической пригодностью для демонстрации и поэтапной сдачи.

## 1. Введение

### 1.1 Проблема

В учебных проектах контроль сроков, статусов и коммуникации часто ведется разрозненно: часть данных — в мессенджерах, часть — в таблицах, часть — в устной коммуникации.  
Это затрудняет проверку фактического прогресса и усложняет итоговую оценку работы ученика.

### 1.2 Цель проекта

Создать единое веб-приложение, где:

- учитель управляет проектами и этапами;
- ученики фиксируют ход выполнения;
- обе стороны ведут рабочую переписку внутри контекста проекта;
- преподаватель получает отчетность по результатам.

### 1.3 Задачи проекта

1. Реализовать регистрацию, вход и ролевую модель (`учитель`, `ученик`).
2. Добавить управление несколькими проектами и этапами.
3. Реализовать хранение прогресса по этапам.
4. Реализовать внутренние сообщения по проекту.
5. Добавить собственный REST API (GET/POST).
6. Обеспечить импорт/экспорт проектных данных в табличном формате.

## 2. Требования и ограничения

### 2.1 Базовые требования ТЗ

- веб-приложение на `Flask`;
- `ORM`-модели;
- `SQLite` (две БД);
- роли учителя и ученика;
- поддержка нескольких проектов;
- CRUD-операции по проектной работе;
- REST API для основных сценариев;
- выгрузка отчетных данных.

### 2.2 Фактические уточнения реализации

1. Экспорт и импорт данных по этапам и аналитике реализованы через `XLSX` (вместо CSV).
2. В карточке этапа ученика хранятся:
   - статус,
   - GitHub-ссылка,
   - комментарий.
3. Дополнительные материалы передаются через сообщения; в сообщениях разрешены изображения с ограничением типа и размера.
4. Для этапов введено бизнес-ограничение уникальности номера в пределах проекта с дружелюбной обработкой конфликтов.

### 2.3 Ограничения текущей версии

- нет email-уведомлений;
- нет редактирования/удаления отправленного сообщения;
- нет асинхронного realtime-чата;
- нет отдельного деплоя/CI-пайплайна в составе данной версии.

## 4. Архитектура системы

### 4.1 Логическая схема

1. Пользователь открывает веб-страницу.
2. Запрос попадает в маршрут Flask.
3. Маршрут проверяет роль и контекст доступа.
4. Выполняется чтение/запись данных через ORM.
5. Формируется HTML или JSON-ответ.

### 4.2 Ролевая модель

#### Учитель

- создает/редактирует проект;
- создает/редактирует/удаляет этап;
- привязывает учеников к проекту;
- просматривает прогресс и аналитику;
- общается с учениками внутри проекта;
- скачивает XLSX-отчеты.

#### Ученик

- видит свои проекты;
- обновляет данные по этапу;
- общается с учителем в контексте проекта.

### 4.3 Проверка доступа

Контроль доступа построен по двум уровням:

1. **роль пользователя** (декоратор `role_required`);
2. **принадлежность к проекту**:
   - учитель может работать только со своими проектами;
   - ученик — только с проектами, где он привязан.

### 4.4 Ключевые модули

- `app/routes.py` — основной слой бизнес-логики.
- `app/models.py` — модели основной базы.
- `app/service_models.py` — модели сервисной базы.
- `app/templates/*.html` — интерфейс для ролей.
- `run.py` — точка запуска приложения.

## 5. Проектирование данных

### 5.1 Основная база (`main.db`)

Содержит предметные сущности:

- пользователи;
- проекты;
- связи проект ↔ ученик;
- этапы;
- прогресс.

### 5.2 Сервисная база (`service.db`)

Содержит:

- сообщения;
- журнал действий;
- журнал API-вызовов.

### 5.3 Причина разделения на две БД

Разделение уменьшает связность:

- учебные сущности и сервисные события развиваются независимо;
- проще обслуживать таблицы с разной интенсивностью записи;
- проще анализировать служебные события отдельно от основной бизнес-части.

### 5.4 Инварианты

1. Email пользователя уникален.
2. Один ученик не может быть привязан к одному проекту дважды.
3. В одном проекте не может быть двух этапов с одинаковым `order_num`.
4. Для пары `(ученик, этап)` существует не более одной записи прогресса.
5. Сообщения пишутся только между валидными участниками проекта.

## 6. Реализация ключевых подсистем

### 6.1 Регистрация, вход, профиль

- Регистрация требует: имя, фамилию, email, пароль, роль.
- Email нормализуется в lowercase и проверяется на уникальность.
- В профиле доступны:
  - обновление ФИО и email;
  - смена пароля (текущий пароль + новый + подтверждение).

### 6.2 Работа учителя с проектами

- создание проекта;
- редактирование названия/описания;
- переход в карточку проекта;
- переход к аналитике проекта.

### 6.3 Работа с этапами

Поддерживаются операции:

- создание этапа;
- редактирование этапа;
- удаление этапа.

Бизнес-правило:

- номер этапа (`order_num`) должен быть уникальным в пределах проекта.
- при конфликте возвращается понятное сообщение, ошибка уровня БД не показывается пользователю.

### 6.4 Прогресс ученика

Для каждого этапа ученик задает:

- статус (`not_started`, `in_progress`, `done`);
- ссылку на GitHub;
- комментарий.

Запись прогресса создается автоматически при первом открытии этапа.

### 6.5 Сообщения и уведомления

- диалоги ведутся внутри конкретного проекта;
- у учителя адресат выбирается из учеников этого проекта;
- у ученика адресат фиксирован (учитель проекта);
- счетчик непрочитанных отображается в шапке;
- при открытии диалога входящие сообщения помечаются как прочитанные.

### 6.6 Импорт этапов из XLSX

Реализован сценарий:

1. скачать шаблон XLSX;
2. заполнить строки этапов;
3. загрузить файл на страницу проекта.

Проверки импорта:

- принимается только `.xlsx`;
- обязательные поля: `order_num`, `title`, `description`, `deadline`;
- поддерживаются русские/английские заголовки колонок;
- строгий режим: любая ошибка отменяет весь импорт;
- дубликаты `order_num` и `title` блокируются.

### 6.7 Экспорт XLSX

#### Отчет проекта

Плоская структура: строка «ученик + этап», с проектными и прогресс-данными.

#### Аналитика проекта

Матричная структура: строки — ученики, колонки — этапы (с дедлайнами), ячейки — статусы.  
Статусы выделяются цветами для быстрого просмотра.

## 7. REST API

### 7.1 Назначение

REST API дает программный доступ к данным проекта и позволяет интеграционно получать списки, статистику и обновлять прогресс/сообщения.

### 7.2 Принципы

- формат обмена: `JSON`;
- доступ к данным ограничен ролью и правами на проект;
- логируются API-обращения в сервисной базе.

### 7.3 Методы API (сводно)

| Метод | URL | Доступ | Назначение |
|---|---|---|---|
| GET | `/api/projects` | учитель/ученик | Список доступных проектов |
| GET | `/api/projects/<project_id>/students` | учитель проекта | Список учеников проекта |
| GET | `/api/projects/<project_id>/stages` | участник проекта | Список этапов проекта |
| GET | `/api/projects/<project_id>/stats` | участник проекта | Агрегированная статистика |
| GET | `/api/students/<student_id>/progress` | ученик (свой) / учитель | Прогресс ученика |
| POST | `/api/messages` | участник проекта | Отправка сообщения |
| POST | `/api/progress` | ученик | Обновление прогресса по этапу |

## 8. Безопасность и валидации

### 8.1 Контроль ролей и контекста

- маршруты учителя/ученика защищены ролевой проверкой;
- маршруты, связанные с проектом, проверяют реальный доступ к проекту;
- API-методы повторно проверяют авторство и права.

### 8.2 Валидация данных

- обязательные поля в формах и API;
- проверка уникальности email и проектных связей;
- проверка уникальности номера этапа;
- корректный формат даты дедлайна;
- ограничение на допустимые статусы.

### 8.3 Защита загрузок

- разрешены только изображения (`png`, `jpg`, `jpeg`, `webp`);
- ограничен максимальный размер;
- имена файлов нормализуются;
- при выдаче файла проверяется, что путь остается внутри `uploads`.

### 8.4 Обработка ошибок БД

Конфликты уникальности обрабатываются через `try/except IntegrityError` с `rollback`, чтобы пользователь получал управляемое сообщение вместо технического traceback.

## Приложение А. Таблица endpoint-ов API

| № | Метод | URL | Роль/доступ | Входные данные | Результат | Типовые ошибки |
|---|---|---|---|---|---|---|
| 1 | GET | `/api/projects` | Авторизованный пользователь | — | Массив проектов | 401 (не авторизован) |
| 2 | GET | `/api/projects/<project_id>/students` | Учитель проекта | `project_id` | Массив учеников | 403/404 |
| 3 | GET | `/api/projects/<project_id>/stages` | Участник проекта | `project_id` | Массив этапов | 403/404 |
| 4 | GET | `/api/projects/<project_id>/stats` | Участник проекта | `project_id` | Объект статистики | 403/404 |

## Приложение Б. Сущности, связи и ограничения БД

### Б.1 Основная БД (`main.db`)

| Сущность | Ключевые поля | Связи | Ограничения |
|---|---|---|---|
| `User` | `id`, `email`, `role`, `first_name`, `last_name` | 1→N с `Project` (как teacher), 1→N с `Progress` | `email` уникален |
| `Project` | `id`, `title`, `teacher_id` | N→1 к `User`, 1→N к `Stage`, 1→N к `ProjectStudent` | `teacher_id` обязателен |
| `ProjectStudent` | `project_id`, `student_id` | N→1 к `Project`, N→1 к `User` | `(project_id, student_id)` уникально |
| `Stage` | `project_id`, `order_num`, `deadline` | N→1 к `Project`, 1→N к `Progress` | `(project_id, order_num)` уникально |
| `Progress` | `student_id`, `stage_id`, `status` | N→1 к `User`, N→1 к `Stage` | `(student_id, stage_id)` уникально |

### Б.2 Сервисная БД (`service.db`)

| Сущность | Ключевые поля | Назначение |
|---|---|---|
| `Message` | `project_id`, `from_user_id`, `to_user_id`, `is_read` | Переписка и read/unread |
| `ActionLog` | `user_id`, `action_type`, `project_id` | Лог действий в UI |
| `ApiLog` | `user_id`, `endpoint`, `method` | Лог API-запросов |

## Приложение В. Чек-лист ручной проверки

### В.1 Проверка роли «Учитель»

- [ ] Зарегистрироваться как учитель.
- [ ] Создать проект.
- [ ] Отредактировать проект.
- [ ] Создать этап с валидными данными.
- [ ] Попробовать создать этап с дублирующим `order_num` и получить корректное сообщение.
- [ ] Отредактировать этап.
- [ ] Удалить этап.
- [ ] Добавить ученика в проект по email.
- [ ] Открыть карточку ученика и проверить статусы этапов.
- [ ] Скачать отчет проекта в XLSX.
- [ ] Открыть аналитику и скачать аналитику в XLSX.

### В.2 Проверка роли «Ученик»

- [ ] Зарегистрироваться как ученик.
- [ ] Войти и открыть свой проект.
- [ ] Открыть этап проекта.
- [ ] Изменить статус, добавить GitHub-ссылку и комментарий.
- [ ] Сохранить прогресс и убедиться, что изменения применены.
- [ ] Проверить отображение статуса «выполнен» в интерфейсе.

### В.3 Проверка сообщений и уведомлений

- [ ] Отправить сообщение от ученика учителю.
- [ ] Проверить счетчик непрочитанных у учителя.
- [ ] Открыть диалог у учителя и убедиться, что сообщение отмечено прочитанным.
- [ ] Отправить ответ учителя ученику.
- [ ] Проверить переход по колокольчику на релевантный диалог.

### В.4 Проверка импорта XLSX

- [ ] Скачать шаблон этапов XLSX.
- [ ] Заполнить 1–2 валидные строки и импортировать.
- [ ] Убедиться, что этапы созданы.
- [ ] Загрузить файл с ошибкой в одной строке и проверить, что импорт целиком отклонен.
- [ ] Проверить отклонение дубликатов `order_num`/`title`.

### В.5 Проверка API (минимум)

- [ ] `GET /api/projects` возвращает доступные проекты.
- [ ] `GET /api/projects/<id>/stages` возвращает этапы.
- [ ] `POST /api/progress` обновляет статус ученика.
- [ ] `POST /api/messages` создает сообщение.
- [ ] Проверить отказ доступа для чужой роли/чужого проекта.
